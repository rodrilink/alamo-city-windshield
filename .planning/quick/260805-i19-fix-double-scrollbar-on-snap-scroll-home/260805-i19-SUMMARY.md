# Phase quick Plan 260805-i19: Fix double scrollbar on snap-scroll home Summary

Eliminated the double scrollbar on `/` by making `(public)/layout.tsx` a passthrough and having `/` own its full viewport (overlay nav + snap container as the only scroller), while `/about` and `/contact` compose their own `TopNav` + `Footer` in normal flow exactly as the shared layout did before.

## What Was Built

### Task 1 — Passthrough layout, `/about` and `/contact` get their own chrome
`src/app/(public)/layout.tsx` now returns `children` directly with no wrapper `div`, no `TopNav`/`Footer` imports, and stays a Server Component (no `'use client'`).

`src/app/(public)/about/page.tsx` and `src/app/(public)/contact/page.tsx` each now render the exact structure the old shared layout provided: an outer `div.flex.min-h-screen.flex-col`, `<TopNav />` (default/non-overlay), a `main.flex-1` wrapping the page's previous content unchanged, then `<Footer />`. Neither page passes an `overlay` prop — both keep the sticky nav in normal flow. Inner markup, data fetching, and existing exports were untouched; neither page already rendered its own `TopNav`/`Footer`, so there was no duplication to resolve.

### Task 2 — TopNav overlay mode + home snap container as the only scroller
`src/components/layout/TopNav.tsx` gained an optional `overlay?: boolean` prop (default `false`). The root `<nav>` className is now built with `cn()`: `overlay ? 'absolute top-0' : 'sticky top-0'` merged with the unchanged `z-50 w-full border-b border-border bg-background/95 backdrop-blur supports-[backdrop-filter]:bg-background/60`. No other markup in the component changed — same inner `div`, same nav links, same phone link, same mobile Sheet.

`src/app/(public)/page.tsx` now wraps the existing snap container in an outer `div.relative.h-dvh.overflow-hidden`. `<TopNav overlay />` is rendered as the first child inside that wrapper, painted over the hero. The snap container keeps `ref={scrollRef}` and its exact className `h-dvh overflow-y-auto snap-y snap-mandatory`, and still passes `scrollRef` to `HeroSection`, `EstimateSection`, and `ServicesSection` — exactly 3 call sites, unchanged. `Footer` was added as a fourth child inside the snap container, after `<ServicesSection />`, wrapped in a `div.snap-start.snap-always` with no height class.

## Footer-Stop Sizing Treatment (the open detail)

**Chosen:** `<div className="snap-start snap-always"><Footer /></div>` — no `h-dvh`, no `min-h-*`, no `flex items-center` wrapper. The stop is exactly the Footer's natural content height (the 3-column grid at `py-8 md:py-12` plus the copyright bar).

**Reasoning:**
- `snap-align: start` (from `snap-start`) means the top edge of this div — which is the top edge of the Footer — aligns with the top of the scroll container on snap. Since it is the last child in the snap container, there is no content below it to leave a "partial slice" visible; the viewport simply shows the Footer plus, if the Footer is shorter than the viewport, empty space below it (page background, `border-t` already delineates where content ends). Snapping back up to `ServicesSection` (which is `h-dvh`) is unaffected since its own top-of-section snap point is unchanged.
- I initially added `min-h-[50vh]` with `flex items-center` to force more vertical presence, but removed it: the plan explicitly says not to give the Footer stop `h-dvh` because it would look sparse when stretched, and an arbitrary `min-h-[50vh]` has the same visual problem (empty space with no content) without any offsetting benefit — the acceptance criteria only require it not carry `h-dvh` and that it not leave a partial section visible above/below when snapped, both of which plain content-height satisfies.
- `snap-always` (paired with `snap-mandatory` on the container) is what forces the wheel to stop on this section rather than skipping past a short target — this is the piece that actually prevents the "ambiguous partial scroll" failure mode the plan warns about, not extra height.
- This could not be fully verified visually (no browser available in this environment) — see Checkpoint section below. If the human verification step (checkpoint step 6/9 area) finds the Footer stop reads as too sparse or leaves unexpected empty space, the fallback per the plan's own guidance would be a modest `min-h-[40vh]` or similar with `flex items-center justify-center` — not `h-dvh`.
