<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Anonymous browser → `/admin/login` | The single unauthenticated entry point into the admin area; accepts attacker-controlled email and password |
| `loginAction` → Supabase Auth | Credentials leave the server over HTTPS; the session cookie comes back and is written via `next/headers` |
| Browser cookie jar → middleware | The `sb-*` session cookie is client-held and must be revalidated server-side on every request, never trusted as a claim |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Information Disclosure | `loginAction` error branches | mitigate | Validation failure and invalid-credential failure both return the identical `ADMIN_COPY.loginGenericError` reference, so a non-existent email is indistinguishable from a wrong password. Only a reachability failure gets a different message, and that message carries no account information |
| T-05-04-02 | Information Disclosure | `console.error` in `loginAction` | mitigate | The password is never included in any logged payload; Task 2's acceptance criteria assert this. Only the error object and (at most) the email reach the server log |
| T-05-04-03 | Tampering | Open redirect via a login destination parameter | mitigate | D-09: `redirect('/admin')` is a hardcoded literal. `loginAction` reads no search param and takes no destination argument; `LoginForm` calls no `useSearchParams`. Both asserted by grep criteria, so the whole vulnerability class is absent rather than validated against |
| T-05-04-04 | Spoofing | Session established without a browser cookie | mitigate | `loginAction` uses the cookie-aware `createClient()` from `server.ts`. Using `createAdminClient()` (`persistSession: false`, no cookie plumbing) would authenticate server-side while leaving the browser unauthenticated; the import is asserted and the file is commented so a future edit does not swap it |
| T-05-04-05 | Session Management | Stale authenticated RSC payload served after logout | mitigate | `logoutAction` calls `revalidatePath('/', 'layout')` after `signOut()`, forcing a fresh render rather than replaying a cached authenticated payload |
| T-05-04-06 | Elevation of Privilege | Forged or replayed session cookie granting `/admin` access | mitigate | Already handled by `src/lib/supabase/middleware.ts`'s `getUser()` (revalidates the JWT signature against the auth server — CVE-2025-29927), verified not reimplemented in Task 1; `getSession` is asserted absent from all of `src/` |
| T-05-04-07 | Elevation of Privilege | Service-role key reaching the browser | mitigate | Task 1 verifies `import 'server-only'` in `admin.ts`, the absent `NEXT_PUBLIC_` prefix, and that no file outside `admin.ts` references `SUPABASE_SERVICE_ROLE_KEY`. This phase's auth actions do not import the admin client at all |
| T-05-04-08 | Spoofing | Credential stuffing / brute force against `/admin/login` | accept | No application-level rate limiting is added. Supabase Auth applies its own request limits upstream, the admin surface is a two-page internal tool with no public signup path (D-05), and adding a custom throttle would need a store this phase has no migration budget for (D-06). Revisit if abuse is observed |
| T-05-04-09 | Denial of Service | Middleware env-guard silently disabling the route guard | accept | Lines 8-12 of `middleware.ts` skip auth when Supabase env vars are absent — an intentional dev escape hatch that is out of scope to change here (verify-only). Task 1 records the caveat so success criterion 1 is verified with `.env.local` loaded rather than against a disabled guard |
</threat_model>
