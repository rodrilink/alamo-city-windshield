<objective>
Deliver `/admin/users`: the admin list (USER-01), add-admin (USER-02), and remove-admin (USER-03) with both D-10 safety guards enforced server-side and a confirmation dialog that names the target email (D-11).

Purpose: D-05 makes `auth.users` the entire admin list — every Supabase Auth user is a full admin, safe only because no public signup path exists anywhere in the application. That also makes removal the most dangerous operation in the phase: deleting a user IS deleting an admin, and removing the last account locks everyone out of the dashboard with no password-reset flow to recover through (D-08), recoverable only from the Supabase dashboard. D-13 puts this on its own route precisely so destructive account actions do not share a long page with read-only analytics.

Output: three Server Actions, one page, and three components — with both guards enforced in the action, never merely hidden in the UI.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form → `addUserAction` | Email and password for a new privileged account arrive untrusted from a client form |
| Browser form → `removeUserAction` | The target user id arrives untrusted; any authenticated admin could submit any id |
| `createAdminClient()` → Supabase Auth | Service-role calls bypass RLS entirely by design; this is the highest-privilege code path in the application |
| `addUserAction` → browser | A live credential is returned in the action's response payload exactly once (D-12) |
