<objective>
Create the `(dashboard)` nested route group and its sidebar layout — the authenticated admin shell (D-14) — structured so it wraps `/admin` and `/admin/users` but deliberately does NOT wrap `/admin/login`.

Purpose: this is the phase's one genuine structural trap. A naive `src/app/(admin)/admin/layout.tsx` would wrap every route under `admin/`, including `admin/login/`, putting a logout button and a signed-in admin's email on the login screen where no session exists. `05-RESEARCH.md`'s Recommended Project Structure resolves this with a second, nested route group: `(admin)/admin/(dashboard)/layout.tsx`, with `(admin)/admin/login/page.tsx` remaining a sibling outside it. `05-PATTERNS.md` also records that this is the **first real (non-passthrough) layout in the repo** — `(public)/layout.tsx` is a documented bare passthrough with no chrome to copy — and that no Server Component in this repo has ever called `.auth.getUser()`, so both the layout shape and the identity read are new call sites. `05-RESEARCH.md`'s Assumptions Log A2 rates the route-group nesting claim MEDIUM confidence and asks that the structure be verified before the rest of the phase is built on top of it, which is why this plan carries a checkpoint.

Output: the `(dashboard)` route group with its layout, a sidebar component, a logout button wired to `logoutAction`, and human confirmation that `/admin/login` renders bare.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Session cookie → `(dashboard)/layout.tsx` | The layout derives the displayed admin identity from a client-held cookie; the JWT must be revalidated server-side, not read as a claim |
| Server Component → Client Component props | Whatever the layout passes to `AdminSidebar` / `LogoutButton` is serialized into the RSC payload and reaches the browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05-01 | Spoofing | Identity read in `(dashboard)/layout.tsx` | mitigate | Uses `supabase.auth.getUser()` through the SSR client, which revalidates the JWT signature against the auth server rather than decoding an unverified cookie claim (CVE-2025-29927). `getSession` is asserted absent |
| T-05-05-02 | Information Disclosure | Props crossing into the browser payload | mitigate | Only `user.email` is passed to `AdminSidebar`; the `user` object, `user.id` and any token are never passed as props, so no identifier beyond the display email is serialized |
| T-05-05-03 | Information Disclosure | Sidebar chrome leaking onto the unauthenticated login page | mitigate | The nested `(dashboard)` route group excludes `login/`; Task 1 asserts `(admin)/admin/layout.tsx` does not exist, and Task 2's blocking human check confirms the rendered login page carries no email and no logout control |
| T-05-05-04 | Session Management | Client-side sign-out leaving the server session intact | mitigate | `LogoutButton` submits a form to the server `logoutAction`; `grep` asserts no `signOut` call exists in the client component, so the cookie clear and `revalidatePath` always happen server-side |
| T-05-05-05 | Elevation of Privilege | Duplicated auth-redirect logic in the layout drifting from the middleware | mitigate | The layout performs no `redirect()`; the middleware remains the single owner of the `/admin/*` guard (AUTH-03), so there is one enforcement point to reason about rather than two that can disagree |
</threat_model>
