    `BookingFormValues` covering the fields BOOK-06 requires and the schema demands: customer first name, last name, phone (all required — the columns are `NOT NULL`), optional VIN, the selected `appt_date` as `'yyyy-MM-dd'` and `appt_time` as `'HH:mm'`, and the honeypot field.     `BookingActionState` as the discriminated result of the booking Server Action, with a `status` field of exactly `'idle' | 'success' | 'slot-taken' | 'error'` (D-10's three outcomes plus the initial state), a `values` field preserving the submitted values so D-09's "preserve entered name/phone/VIN" requirement is expressible, optional per-field errors, and an optional pre-written user-facing message. Add TSDoc on the `status` union stating that `'slot-taken'` is reachable ONLY from Postgres error code `23505` and that every other failure is `'error'` — and that `'error'` must never disable the slot, since it may still be free.

    `ContactActionState` following the same shape minus `'slot-taken'`, since `contacts` carries no unique constraint.

Per PATTERNS.md, the availability read must be able to express "the read failed" distinctly from "nothing is booked" — an empty list and a failed query must not be the same value, because treating a database outage as a fully-open calendar would directly contradict D-08. Model that explicitly.

    Do not write Zod schemas in this file — those come in plan `04-05` where they are co-located with the Server Actions that re-run them server-side. This file is types only.
