<objective>
Build the server-side data layer: availability reads for the calendar, and both Server Actions that write to Supabase with the full set of D-08 through D-15 controls.

Purpose: This is where the phase's core guarantee lives. Double-booking is made structurally impossible by attempting the insert and catching the `UNIQUE` violation — never by checking first, which always has a race window. It is also where every untrusted input is gated: the honeypot, the Zod re-validation, and the D-15 slot-legality re-derivation that stops a crafted `appt_time` the `UNIQUE` constraint would happily accept.

This repo has **zero** Server Action precedent — D-13 makes Phase 4 the first. Follow the shape below rather than searching for an analog.

Output: `booking-availability.ts`, the two Zod schema modules, and the two Server Actions.
</objective>

    1. **Honeypot (D-14).** If the honeypot field is non-empty, return without writing anything. Return a state indistinguishable from success to the bot — do not reveal that the submission was discarded. D-14 applies the honeypot to bookings even though CONT-03 only requires it for contacts, because `bookings` carries `public_insert` RLS with `WITH CHECK (true)` and the `UNIQUE` constraint means a scripted insert permanently blocks that slot from real customers.
    2. **Zod re-validation.** Parse `formData` through the booking schema. The client already validated; this run is the untrusted-input gate, because a crafted POST never touches the client resolver. On failure return `status: 'error'` with field errors and the preserved values.
    3. **Slot-legality re-validation (D-15).** Run the Task 2 validator. Reject an off-grid, past-closing, or Sunday `appt_time` here. Per RESEARCH.md Pitfall 4, this failure is a different class from a race — return `status: 'error'`, NOT `'slot-taken'`, and do not mark the slot unavailable, because the slot was never real.
    4. **Insert (D-08).** Call `createAdminClient()` and insert into `bookings` with `status: 'pending'` (D-12 — nothing is `'confirmed'` until the owner confirms by phone) and the `service_type` column left at its `'replacement'` default. Attempt the insert directly. **Never SELECT to check availability first** — any check-then-insert has a race window, and the `UNIQUE (appt_date, appt_time)` constraint is the only real guarantee.
    5. **Branch on the result (D-10).** `error.code === '23505'` — and only that code — means the slot was taken; return `status: 'slot-taken'` with `BOOKING_COPY`'s slot-taken message. Any other error returns `status: 'error'` with the generic message plus `BUSINESS.phone`. Branch on `error.code`, never on `error.message` — PostgREST message text is not a stable contract across versions. Log the full error server-side with `console.error`; never place `error.message`/`details`/`hint` into the returned state.
    6. **Preserve values (D-09).** Every non-success return carries the submitted values so the customer keeps their name, phone, and VIN and only has to re-pick a time.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser → Server Action | Unauthenticated public input crosses into a service-role database write |
| Server Action → Postgres | The service-role client bypasses all RLS, so application-level validation is the only gate |
| Supabase error object → browser | Raw Postgres/PostgREST diagnostics must never reach the client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05-01 | Tampering | Crafted `appt_time` outside the legal grid (e.g. `03:00`) | mitigate | D-15: `createBooking` re-runs `generateSlotsForDate` for the submitted date and rejects any non-member time before the insert; pinned by a schema test asserting `'03:00'` and Saturday `'13:30'` are rejected |
| T-04-05-02 | Tampering | Client-supplied `vehicle_desc` written to the DB and later rendered in Phase 5's admin table | mitigate | D-19: `vehicle_desc` is never read from `formData`; it comes only from plan `04-06`'s server-side re-decode. Asserted by a grep in acceptance criteria. |
| T-04-05-03 | Denial of Service | Scripted insert occupying a slot permanently via the `UNIQUE` constraint | mitigate | D-14: honeypot on the booking form (not just contact), checked before any database call, returning silently so the bot gets no signal |
| T-04-05-04 | Denial of Service | Targeted script that skips the honeypot and squats every slot | accept | Explicitly deferred by the user in CONTEXT.md Deferred Ideas — Vercel serverless has no shared memory so real rate limiting needs external state (Upstash/Postgres counter).
