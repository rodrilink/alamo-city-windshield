<objective>
Fire a `page_view` event for every public-route visit (ANLY-02) via a single invisible client tracker mounted once in the `(public)` layout, deduped per path per session.

Purpose: the ADMIN-02 visitors chart and the "Total Visitors" summary card have been reading zero rows since Phase 5 because nothing writes them. This plan is the producer. D-05 puts the tracker in the layout rather than in each page because the public pages are mixed component types — `(public)/page.tsx` is `'use client'` while `/about`, `/contact` and `/book` are Server Components — and a layout-level client tracker covers all of them uniformly while also catching client-side navigation a server-render call would miss.

Output: `src/components/analytics/PageViewTracker.tsx` (new) and a two-line edit to `src/app/(public)/layout.tsx`.
</objective>

    Inside the effect, implement the D-08 dedupe — one row per distinct pathname per session:
    - Build a session-storage key by prefixing the pathname with a module-level named constant (declare it as a const at module scope rather than inlining the string; the repo's convention is named-constant-over-inline-literal).     - Read `window.sessionStorage.getItem(key)` inside its own `try`/`catch`. On any throw — private browsing, storage disabled, storage quota — treat the result as "not yet seen" and proceed to fire, rather than throwing or silently disabling tracking. This read must never throw out of the effect.

    - Then mark the key as seen with `window.sessionStorage.setItem(key, ...)`, also wrapped in its own `try`/`catch` with an empty body. Dedupe is best-effort; a storage write failure must not affect anything. Comment that the empty catch is deliberate.

    Import `ANALYTICS_EVENTS` from `@/lib/analytics/events` and `trackBrowserEvent` from `@/lib/analytics/track-event`. Do NOT declare the string `'page_view'` anywhere in this file — the whole point of D-01 is that the literal lives in exactly one module.

    Do NOT add any `console.log` / `console.error` / `console.warn` anywhere in this file. Browser-side tracking is silent per D-12.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `analytics_events` via anon key | The tracker writes from untrusted client code under the pre-existing `public_insert_analytics` RLS policy (`WITH CHECK (true)`). The anon key and the insert shape are both visible in the browser bundle by design. |
| `usePathname()` value → the `page` column | A pathname is client-derived. It is persisted verbatim into a `TEXT` column and later rendered on the admin dashboard. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02-01 | Spoofing / Tampering | Forged `page_view` inserts with the public anon key | accept | Inherited from T-06-01-01. The permissive insert policy is pre-existing Phase 1 infrastructure, and D-09 chose it over a new `POST /api/track` endpoint specifically to avoid adding a new abuse surface. A forger inflates only an internal vanity metric; no authorization, billing, or user-visible behavior depends on the count. Documented so nobody later mistakes the visitor count for an integrity-bearing number. |
| T-06-02-02 | Information disclosure | Pathname written to the `page` column | mitigate | Only `usePathname()` is captured — the route path with no query string, no hash, and no `useSearchParams()` read. Public routes (`/`, `/about`, `/contact`, `/book`) carry no identifiers in the path, so no PII is persisted. D-02 additionally leaves `metadata` null, so no referrer, viewport, or session identifier is collected. Task 1's action forbids adding any other field. |
| T-06-02-03 | Information disclosure | Admin route paths leaking into analytics | mitigate | The tracker mounts only in `(public)/layout.tsx`; `(admin)` has a separate layout tree, so admin pathnames are structurally uncapturable (D-06). Enforced by a Task 2 acceptance criterion asserting no admin layout references `PageViewTracker`. |
| T-06-02-04 | Information disclosure | Service-role key leaking into the browser bundle | mitigate | The tracker imports only `trackBrowserEvent` and `ANALYTICS_EVENTS`. `trackServerEvent`'s transitive `createAdminClient` import carries `import 'server-only'`, so any accidental server-path import from this Client Component fails the build. Task 2's `npm run build` acceptance criterion is the enforcing check. |
| T-06-02-05 | Denial of service | Storage exceptions or a hung insert breaking the page | mitigate | Both `sessionStorage` accesses are individually wrapped in `try`/`catch`, and the insert is `void`-ed inside `useEffect` so a rejected promise cannot propagate into React's render path. `trackBrowserEvent` swallows internally as well. Net effect: the page renders identically whether tracking succeeds, fails, or is impossible. |
| T-06-02-06 | Repudiation | Under-counting from over-aggressive dedupe | accept | D-08 deliberately trades raw view counts for per-session-per-path semantics. The consequence is recorded explicitly: the "Total Visitors" card counts distinct page-visits per session, not unique people. Task 1 requires that statement in the component header so downstream copy cannot misdescribe it. |
| T-06-02-SC | Tampering | npm/pip/cargo installs | n/a | This plan installs no packages. |
</threat_model>
