<objective>
Make the dashboard's Visitors KPI and Visitors chart count **distinct browser sessions** instead of `page_view` rows.

Why: human verification of plan 06-05 found the KPI reads 1 → 2 → 3 as a single person navigates Home → About → Contact. That is the code behaving exactly as 06-02 designed it (D-08 dedupes per *path* per session, so N distinct paths write N rows) and exactly as `getSummaryTotals` reads it (a plain `count: 'exact'` over all `page_view` rows). The result is a card labelled "Visitors" reporting page views — a single visitor inflates it by however many pages they browse. The D-08 comment in `PageViewTracker.tsx` acknowledged this consequence in prose; a code comment is not a fix for a misleading number on an owner-facing dashboard.

Scope decision (user-selected): count real sessions. A `session_id` is generated once per browser session and stored on each row; both the KPI and the chart count distinct sessions.

Deliberate limitation to record, not solve: `session_id` lives in `sessionStorage`, so its lifetime matches the existing D-08 dedupe key. The same person in a new tab, or returning tomorrow, counts as a new visitor. This is a *session* count, not a unique-people count — true cross-visit identity requires a persistent identifier and carries privacy implications this plan deliberately does not take on. The card's meaning becomes "visits" in the ordinary web-analytics sense, which is what the label reasonably implies and is a large improvement over page views.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-06-01 | Spoofing | Client-supplied session_id | accept | `session_id` is browser-generated and fully client-controlled — a caller can send any value and inflate or deflate the visitor count. This is inherent to client-side analytics and matches the pre-existing posture: `public_insert_analytics` is already `WITH CHECK (true)`, so anyone could already insert arbitrary `page_view` rows. The metric is directional business insight, not an audited figure. Server-issued session cookies would be the fix if it ever needs to be trustworthy. |
| T-06-06-02 | Information disclosure | session_id as a tracking identifier | mitigate | Scoped to `sessionStorage`, so it dies with the tab and cannot correlate a person across visits. Deliberately NOT a cookie or localStorage value. It is a random opaque value carrying no personal data and is never joined to `contacts` or `bookings`. |
| T-06-06-03 | Tampering | Migration on a live table | mitigate | Additive only: one nullable column plus an index. No existing column, constraint or RLS policy is altered, and no data is backfilled or rewritten. `IF NOT EXISTS` guards make it re-runnable. Worst case on failure is that the column is absent and the KPI reads 0 — visibly wrong rather than silently wrong. |
| T-06-06-04 | Denial of service | Unbounded distinct-session scan | accept | Both reads now fetch `session_id` rows rather than a bare count, so payload grows with traffic. At this business's scale that is negligible, and the new index covers both queries. If volume ever makes it matter, the correct fix is a Postgres RPC doing `count(distinct session_id)` server-side. Recorded, not pre-optimized. |
| T-06-06-SC | Tampering | npm/pip/cargo installs | n/a | This plan installs no packages. |
</threat_model>
