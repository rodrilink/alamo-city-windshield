<objective>
Fire `contact_submit` (ANLY-04) and `booking_created` (ANLY-05) inside the two existing Server Actions, on the confirmed-success path only.

Purpose: D-09 writes each event from where it already knows it happened. Both actions already call `createAdminClient()` and already own the exact outcome, so no new endpoint and no client round-trip is needed.

⚠ **The critical trap (D-11):** both actions contain a honeypot early-return that returns `{ status: 'success', values }` **without inserting anything**, to give a bot no signal that its submission was discarded. Firing an event there would let bot submissions inflate `contact_submit` and would produce `booking_created` rows with no corresponding `bookings` row — making the analytics table disagree with the source table. Events fire only after the insert returns without error.

Output: two modified files, one call site each, with no change to any returned action state.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → `createContact` / `createBooking` Server Actions | Unauthenticated POST endpoints reachable by a crafted request that never touches the client-side Zod resolver. Both already run honeypot → Zod re-validation as their untrusted-input gate. |
| Server Action → `analytics_events` (service-role) | `trackServerEvent` writes with an RLS-bypassing identity, server-side only. |
| `analytics_events` ↔ `contacts` / `bookings` | The event table is expected to agree with the source tables it mirrors. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-04-01 | Tampering | Bot inflating `contact_submit` / `booking_created` via the honeypot path | mitigate | This is the plan's headline risk. Both actions return `{ status: 'success' }` from the honeypot branch **without inserting**, precisely so a bot gets no signal. Placing an event there would hand scripted submissions a working write primitive into the metrics table. Mitigated by placing both calls strictly downstream of the insert's error check, and enforced by acceptance criteria that assert no `trackServerEvent(` substring exists anywhere before the honeypot check in either file. |
| T-06-04-02 | Repudiation | Analytics disagreeing with the source tables | mitigate | A `booking_created` row with no matching `bookings` row, or a `contact_submit` with no `contacts` row, makes the two sources irreconcilable and undermines every downstream number. Prevented by firing only after the Supabase insert returned no error — past the `'23505'` slot-taken race (no row was created), past the generic error branch, and outside the `catch`. Six acceptance criteria assert the call's position relative to each of those branches. |
| T-06-04-03 | Information disclosure | Event payload leaking submitter PII | mitigate | Both calls pass only the event-type constant — no name, phone, address, VIN, or appointment time. D-02 leaves `metadata` null. Task actions explicitly forbid passing `page` or `vin` here, and the acceptance criteria pin the single-argument call shape. The PII already lives, appropriately, in `contacts` / `bookings`. |
| T-06-04-04 | Denial of service | Added latency on the user's submit path | mitigate | D-10 accepts one extra same-region Supabase insert on submit, with no retry loop and no timeout wrapper (a timeout was explicitly rejected as more machinery than a same-region insert warrants). The user's own insert has already completed and its result is already determined before the tracking call runs, so the worst case is a slower success response, never a lost booking or contact. |
| T-06-04-05 | Tampering | A tracking failure corrupting the returned action state | mitigate | `trackServerEvent` returns `void`, swallows every failure internally, and is neither wrapped nor branched on at either call site. The `ContactActionState` / `BookingActionState` returned on every path is byte-identical to before this plan — this is the direct implementation of ANLY-06. Enforced by the unchanged-`return {`-count acceptance criteria (5 and 7 respectively). |
| T-06-04-SC | Tampering | npm/pip/cargo installs | n/a | This plan installs no packages. |
</threat_model>
